# الفحص الأمني الداخلي الشامل

هذا هو بديل فحص الاختراق الخارجي بقرار صفوان. الهدف أن **تحاول اختراق البوابة فعلاً** لا أن تراجعها نظرياً فقط.

## قواعد الاشتباك

هذه القواعد ثابتة لا استثناء فيها:

- **النطاق المسموح:** الاختبار على البيئة المحلية (`localhost`) أو البيئة التجريبية فقط.
- **الإنتاج ممنوع:** لا يُختبر الخادم الحقيقي ولا `ejaz.sa` إلا بإذن مكتوب من صفوان في المحادثة لكل جولة.
- **لا بيانات حقيقية:** بيانات تجريبية من المصانع (Factories) فقط.
- **لا خدمات خارجية:** لا هجمات حرمان من الخدمة، ولا فحص لأي خدمة خارجية (ميسر، مزود الرسائل، مايكروسوفت).
- **أدوات الهجوم:** لا تُثبَّت على جهاز صفوان. تعمل داخل حاويات مؤقتة تُحذف بعد الفحص.
- **ما يُحفظ في قيت:** تقرير الثغرات، والاختبارات المانعة لعودتها. أما سكربتات الاستغلال فلا.

## المرحلة ١ — المراجعة سطراً سطراً

1. اقرأ `docs/security.md` كاملاً.
2. اسرد كل مسار:
   ```bash
   docker compose exec -T app php artisan route:list --json
   ```
   ثم اسرد كل مكون Livewire، وكل مورد Filament، وكل أمر Artisan، وكل مهمة في الطابور.
3. لكل عنصر، اقرأ الشيفرة سطراً سطراً، وتحقق من القائمة المرجعية (OWASP ASVS المستوى 2):
   - **الصلاحيات:** هل يوجد `authorize` أو Policy؟ هل يمكن الوصول لسجل غيره بتغيير الرقم (IDOR)؟ هل خصائص Livewire العامة محمية (`#[Locked]`)؟
   - **المدخلات:** هل كل حقل له قاعدة تحقق صريحة؟ هل `fill($request->all())` أو `$guarded = []` موجودة في أي مكان؟
   - **المخرجات:** هل يُستخدم `{!! !!}` على محتوى غير منقّى؟ هل يُبنى JavaScript أو روابط من مدخلات المستخدم؟
   - **الاستعلامات:** هل توجد `DB::raw` أو `whereRaw` أو `orderByRaw` بمدخلات المستخدم؟
   - **الملفات:** هل يُتحقق من النوع الحقيقي والحجم؟ هل القرص خاص؟ هل الروابط مؤقتة؟ هل يمكن التلاعب بالمسار؟
   - **الحسابات:** حدود المحاولات، والتحقق الثنائي، وصلاحية الرموز، وتجديد الجلسة، وكشف وجود الحسابات.
   - **الأسرار:** هل توجد مفاتيح أو كلمات مرور في الشيفرة أو في السجلات أو في رسائل الخطأ؟
   - **السجلات:** هل تُسجَّل بيانات شخصية أو رموز لا داعي لها؟
   - **الإعدادات:** `APP_DEBUG`، ورؤوس الحماية، وملفات تعريف الارتباط (`Secure` و`HttpOnly` و`SameSite`)، وCORS.
4. سجّل كل ملاحظة فوراً: الملف والسطر، والخطورة، وسيناريو الاستغلال.

## المرحلة ٢ — محاولة الاختراق الفعلية

على البيئة المحلية، بحسابات تجريبية لكل دور (مستفيد، ومحكّم، ومحرر، ومشرف):

1. **الفحص الآلي:** OWASP ZAP في حاوية مؤقتة:
   ```bash
   docker run --rm --network host ghcr.io/zaproxy/zaproxy:stable zap-full-scan.py -t http://localhost:8000
   ```
   مرة كزائر، ومرة بجلسة مستخدم مسجّل. احفظ التقرير في `storage/security-audit/` (غير متتبع في قيت).
2. **الهجوم اليدوي الموجّه.** اكتب لكل محاولة اختبار Pest يجربها فعلاً:
   - **IDOR:** مستخدم (أ) يطلب سجلات المستخدم (ب) بكل مسار يحوي رقماً أو معرّفاً.
   - **رفع الصلاحية:** مستفيد يطلب مسارات الإدارة وإجراءات Filament وLivewire مباشرة، ويرسل حقولاً إضافية (`role` و`is_active` و`email_verified_at`).
   - **تجاوز التحقق الثنائي:** الوصول إلى `/admin` بعد كلمة المرور وقبل الرمز، وإعادة استخدام رمز، وتخمين رموز الاسترداد.
   - **تجاوز حدود المحاولات:** تغيير صيغة المعرّف، وتغيير رأس `X-Forwarded-For` بلا وكيل موثوق، والطلبات المتزامنة.
   - **الحقن:** حمولات SQL وXSS (المخزّن والمنعكس) في كل حقل نصي يُعرض لاحقاً، خاصة في لوحة الإدارة، لأن ما يكتبه المستفيد يقرؤه المشرف.
   - **الملفات:** رفع PHP متنكر في صورة، وSVG بسكربت، وملف ضخم، واسم ملف بمسار (`../../`).
   - **CSRF والجلسات:** طلبات بلا رمز، وتثبيت الجلسة، وبقاء الجلسة بعد تغيير كلمة المرور أو الإيقاف.
   - **إعادة توجيه مفتوحة:** معامل `intended` أو أي رابط إعادة توجيه بقيمة خارجية.
   - **منطق الأعمال:** تقديم مكرر في المسابقة، وتسجيل يتجاوز المقاعد، وتعديل بعد الاعتماد، وسحب يمكن التلاعب به.
   - **إغراق الرسائل والبريد:** هل يمكن استنفاد سقف الرسائل أو إرسال بريد لعناوين عشوائية؟
3. **أي محاولة تنجح ثغرةٌ:** يُكتب لها إصلاح، والاختبار نفسه يبقى في `tests/Feature/Security/` ليمنع عودتها.

## المرحلة ٣ — الإصلاح والتحقق

1. أصلح الثغرات بترتيب الخطورة: حرجة، ثم عالية، ثم متوسطة.
2. كل إصلاح في حفظ مستقل: `fix(security): ...`
3. أعد تشغيل ZAP والاختبارات حتى لا تبقى حرجة ولا عالية.
4. `composer check` و`composer audit` و`npm audit` بلا أخطاء.

## المرحلة ٤ — التقرير

اكتب `docs/security/audit-<التاريخ>.md` بالعربية:
- النطاق، والتاريخ، والحسابات والأدوات المستخدمة.
- إحصاء الثغرات حسب الخطورة: ما وُجد، وما أُصلح، وما بقي ولماذا.
- لكل ثغرة: الوصف، وسيناريو الاستغلال، والإصلاح، والحفظ، والاختبار المانع.
- ما لم يُختبر، بوضوح (مثل البنية التحتية للإنتاج قبل وجودها).
- **الحكم:** جاهز للإطلاق، أو غير جاهز وما المطلوب.

ثم اطلب من الوكيل `security-reviewer` مراجعة التقرير والإصلاحات بعين مستقلة. ويراجعها المشرف الخارجي قبل الدمج.
